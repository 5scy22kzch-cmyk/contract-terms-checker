# Сверка условий договоров поставки — прототип

Локальное веб-приложение для специалиста по закупкам. Загружаете TXT-файлы (договоры, допсоглашения, письма, проекты) и получаете таблицу по договорам: номер, поставщик, сумма и срок поставки на дату проверки. Для каждого значения указаны файл, точная цитата и переход к абзацу исходного текста. Несогласованные изменения показываются отдельно.

## Запуск

Нужен только **Node.js 18+**. npm-зависимостей нет, `npm install` не нужен.

```bash
node server.js
```

Откройте http://localhost:8080. Порт меняется переменной `PORT`, папка с примерами — переменной `SAMPLES_DIR` (по умолчанию `./Documents`).

```bash
npm test
```

Тесты используют встроенный `node:test`: 23 проверки на исходных файлах и синтетических документах.

## Как пользоваться

1. **Загрузить TXT-файлы** (кнопкой или перетаскиванием). Кнопка **«Загрузить примеры»** подставляет файлы из `Documents/` — это просто быстрый способ загрузить их для демо. Кодировка определяется автоматически: UTF-8 или Windows-1251. Файл с тем же именем заменяет ранее загруженный, так что исправленный договор можно загрузить повторно.
2. **Дата проверки** по умолчанию 10.03.2026. При её изменении всё пересчитывается.
3. **Таблица договоров.** Нажмите на строку, и откроются основания:
   - цитата и ссылка «открыть абзац»: справа откроется документ с подсвеченным фрагментом;
   - история изменения поля: было по договору → стало по ДС № N с такой-то даты;
   - суммы, которые не приняты как стоимость (аванс, лимит), с объяснением;
   - связанные документы и их влияние: «Применено», «Проект: не подписан», «Письмо: предложение», «Вступает в силу позже даты проверки», «Требует проверки».
4. **Вопросы.** Строка ввода и четыре вопроса-примера в виде чипов. Вопрос разбирается правилами: номер договора, поле («срок» или «сумма»), «на <дату>» (пересчёт на эту дату), «раньше/до <даты>» (фильтр по сроку поставки). Произвольный чат не поддерживается.

| Вопрос | Ответ прототипа на 10.03.2026 |
|---|---|
| Срок по STN-101 на 10 марта 2026? | **30.04.2026** — ДС № 1 (вступило 01.03.2026), было 15.04.2026. Отдельно: проект ДС № 2 предлагает 10.05.2026, он не подписан |
| Сумма STN-102? | **840 000 ₽** (п. 2.1). Аванс 252 000 ₽ не принят как сумма договора |
| Сумма STN-103? | **нет данных**: стоимость определена приложением № 1, которого нет в комплекте. Лимит 600 000 ₽ — не цена договора |
| Поставка раньше 01.04.2026 и несогласованные изменения срока? | **STN-102 (20.03.2026)**. Есть несогласованное предложение из письма от 05.03.2026 перенести на 27.03.2026 |

Ответы не зашиты в код: в тестах файлы переименовываются и перемешиваются, подставляются новые договоры и изменённые поля.

## Структура

```
server.js            статический сервер + /api/samples (примеры из Documents/)
src/text.js          абзацы, предложения, даты, суммы, сумма прописью, организации
src/engine.js        типы документов, статусы, связывание, применение ДС, итог по полям
src/questions.js     разбор вопроса и сборка ответа с источниками
public/              интерфейс (HTML + JS-модуль без фреймворков)
test/engine.test.js  тесты
Documents/           учебные документы
```

## Известные ограничения

- Работа на правилах рассчитана на формат учебных документов: заголовок с типом, строка «Статус:», пункты вида «2.1.», формулы «изложить в следующей редакции: «…»» или «изменить … на …». Документ другого формата скорее получит «нет данных» или «требует проверки», чем неверное значение, но совсем без ошибок это не гарантируется.
- Тип документа определяется по первой строке. Связь с договором — по номеру договора в тексте. Документ без номера, с номером незагруженного договора или с несколькими номерами не привязывается и помечается.
- Подписание определяется по тексту строки «Статус:». ЭЦП и ЭДО не проверяются.
- Извлекаются только сумма и срок поставки. Неустойка, условия оплаты и частичные поставки не извлекаются.
- Суммы — только в рублях. Даты — `ДД.ММ.ГГГГ` и «15 апреля 2026».
- Приложения и спецификации не разбираются. Если сумма вынесена в приложение, будет «нет данных».
- Данные хранятся только в памяти вкладки и после перезагрузки пропадают. Обработка идёт в браузере, на сервер документы не отправляются.
- OCR, PDF и DOCX, авторизация, многопользовательский режим не входят в объём прототипа.

# Записка

## Для кого

Для специалиста по закупкам, который сверяет условия поставок: сумму, срок и действующие изменения на конкретную дату. Ему нужно быстро получить ответ и при этом проверить его по первоисточнику, не перечитывая весь комплект документов. Главная ценность — не автоматизация сама по себе, а **доверие**: каждое значение можно проверить одним кликом, а сомнительные случаи прямо отмечены.

## Пять вопросов клиенту перед развитием

1. Откуда и в каком виде приходят документы в реальности: сканы, DOCX, ЭДО, учётная система? Насколько однородны шаблоны договоров у разных поставщиков?
2. Что ещё меняет условия, кроме ДС: спецификации, протоколы разногласий, заявки, счета? Как поступать, если сумма задана в приложении?
3. Что считать доказательством подписания: отметку в тексте, ЭЦП в ЭДО, статус в учётной системе?
4. Какие поля нужны следующими (неустойка, оплата, частичные поставки, валюта) и какие решения закупщик по ним принимает?
5. Что происходит после «требует проверки»: кто проверяет, нужно ли фиксировать решение и историю, нужна ли выгрузка или интеграция? Какая цена ошибки — штраф, срыв поставки?

## Принятые допущения

- Условия меняет только ДС, которое подписано обеими сторонами и вступило в силу к дате проверки (на эту дату оно подписано, и дата вступления в силу ≤ даты проверки). Письма и проекты не меняют условия никогда. Даты в именах файлов и порядок загрузки не учитываются.
- Если в ДС не указана дата вступления в силу, оно не применяется и помечается «требует проверки». Формулировка «вступает в силу с даты подписания» трактуется как дата подписания.
- Несколько действующих ДС применяются по дате вступления в силу, затем по дате подписания и номеру. Если два ДС вступают в силу в один день и задают разные значения, ставится «требует проверки».
- Сумма договора — только та, что явно названа общей или итоговой стоимостью (ценой договора). Аванс, лимит и неустойка суммой договора не считаются. Если сумма цифрами расходится с суммой прописью, ставится «требует проверки».
- Срок поставки — дата в предложении о поставке. Сроки оплаты и приёмки не учитываются.
- Дата проверки по умолчанию 10.03.2026 и задаётся в интерфейсе.

## Метрики

1. **Доля уверенных ошибок**: значения со статусом «подтверждено», которые расходятся с ручной разметкой. Цель — 0. Это главный риск: закупщик доверится неверной цифре. Рядом считается точность значений и цитат на размеченной выборке.
2. **Доля полей без ручной работы**: подтверждено ÷ всех полей. Вместе с временем сверки одного договора (до и после) показывает реальную пользу. Растёт при расширении правил и не должна расти за счёт метрики 1.

## Архитектура

```
TXT (UTF-8/1251) ──► text.js: абзацы → предложения → даты/суммы/организации (с позициями)
                         │
                         ▼
engine.js:  тип документа (заголовок) ─ статус (строка «Статус:») ─ дата вступления в силу
            связывание с договором по номеру в тексте
            базовые значения из пунктов договора
            для каждого ДС на дату проверки: применено / проект / ещё не действует / неясно
            применённые ДС: замена пунктов «изложить в редакции» → повторное извлечение → история
            остальные: предложения (не меняют значения)
                         │
                         ▼
поле = {значение | «нет данных», статус ok/review/missing, цитата (файл, абзац, смещения), история}
                         │
              ┌──────────┴──────────┐
        таблица + карточки     questions.js: разбор вопроса правилами → ответ с источниками
```

Вся обработка выполняется в браузере. `server.js` только отдаёт статические файлы. Модули `src/` одни и те же в браузере и в тестах.

### Три ключевых решения и компромиссы

1. **Правила вместо LLM.** Результат детерминирован и воспроизводим, цитата — всегда точная подстрока исходника со смещениями, не нужны ключи и платные API, легко писать тесты. Минус: хрупкость к новым формулировкам, каждую придётся добавлять правилом. Развитие — LLM как дополнительный извлекатель кандидатов с жёсткой проверкой: цитата должна дословно найтись в документе, иначе ставится «требует проверки».
2. **ДС применяется как замена пункта с повторным извлечением**, а не как «последнее упомянутое значение». Так получаются правильный источник (цитата из ДС), история «было → стало» и корректная работа с несколькими ДС. Минус: зависимость от формулы «изложить в редакции». Для прямых формулировок («изменить срок поставки на …») есть запасной путь, остальное уходит в «требует проверки».
3. **Консервативность.** При любой неоднозначности (несколько значений, расхождение с суммой прописью, неясный статус, неизвестный договор) показывается «нет данных» или «требует проверки», а не догадка. Минус: больше ручных проверок, поэтому вторая метрика следит за долей полей без ручной работы.

### Что изменится при 100 000 документов и правах доступа

- Обработка уходит на сервер: асинхронная очередь загрузки, извлечение один раз при поступлении документа, результаты с версиями правил хранятся в БД (Postgres). Связи «договор — документы» хранятся в БД, а не пересчитываются в браузере. Полнотекстовый индекс нужен для поиска.
- Связывание дополнительно учитывает контрагента и ИНН, нужна дедупликация версий одного файла. Нужен OCR для сканов.
- Права доступа проверяются на уровне строк (подразделение, контрагент, договор) **до** поиска и агрегации. Если значение изменено документом, к которому у пользователя нет доступа, это должно быть видно («есть изменение в недоступном документе»), но без цитаты. Нужен аудит просмотров и решений.
- Ответы на вопросы — запросы к БД по извлечённым полям, а не разбор всех текстов.

### Три следующих улучшения (по приоритету)

1. **Размеченный набор реальных документов и регрессия по метрикам.** Без этого нельзя безопасно расширять правила или подключать LLM.
2. **Подтверждение и исправление значения пользователем** с фиксацией, кто и когда решил («требует проверки» → «проверено»), плюс экспорт таблицы. Это закрывает рабочий цикл закупщика.
3. **Новые поля и источники**: неустойка и условия оплаты (с цитатой), разбор спецификаций и приложений, DOCX и PDF.

# Отчёт о вайбкодинге

**Инструмент:** Claude Code (десктопное приложение), модель Claude Opus 5.5. Код, тесты и этот README сгенерированы в одной сессии. Каждый результат проверялся запуском тестов и в браузере.

**Характерные запросы к ИИ:**

1. «Глянь тестовое. Нужно сделать :)» — со ссылкой на папку с заданием (DOCX) и документами. ИИ сам прочитал задание, выбрал стек (Node без зависимостей, правила вместо LLM) и разбил работу на этапы: движок → вопросы → интерфейс → тесты → проверка в браузере → README.

**Ошибки ИИ и как они найдены:**

- **Ложная «дата вступления в силу» у договоров.** Правило искало «вступ… в силу» и срабатывало на общий пункт 5.1 договора («…наступления указанной в нём даты вступления в силу»). В списке документов у договоров появилось «вступает в силу 05.02.2026». Тесты прошли, потому что на итоговые значения это не повлияло. Ошибку заметили при визуальной проверке интерфейса в браузере. Исправление: правило сужено до глагольных форм («вступает/вступит в силу»), для договоров дата не вычисляется. Добавлен регрессионный тест.
- **Ни один документ не привязался к договору.** Для поиска номера ИИ применил к тексту ту же нормализацию, что и к номеру, включая удаление пробелов. «ДОГОВОРУ STN-101» превращалось в «ДОГОВОРУSTN-101», и проверка границы слова не срабатывала. Найдено первым же прогоном на исходных файлах: ДС и письмо получили статус «ссылается на договор, который не загружен». Исправлено отдельной нормализацией текста.
- **Мелочи интерфейса**, найденные по скриншотам: правило `display: flex` перекрывало атрибут `hidden`, и пустая панель просмотра была видна сразу. На ширине телефона таблица документов давала горизонтальную прокрутку.

**Как проверялся результат:** `npm test` (исходный набор и синтетические случаи: неподписанное ДС, ДС с будущей датой вступления, без даты вступления, подписанное одной стороной, порядок ДС не по имени файла, новый договор того же формата, изменённое поле, CRLF, неизвестный договор, расхождение суммы цифрами и прописью). Также ручной прогон четырёх вопросов в браузере, загрузка файла в Windows-1251 и проверка вёрстки на ширине телефона.

**Фактические затраты времени:** 1 час.
